# Gong_comfyui

ComfyUI 自定义节点与工作流合集，面向本地 MiniMax H3 视频生成。

作者：**宫鸿翔 (Hongxiang Gong)**

---

## 一、这是什么

本仓库只包含两样东西：

1. **三条 ComfyUI 工作流**（全部基于 MiniMax H3 的 `ref2va` 参考生视频能力）：

   | 工作流 | 作用 |
   |---|---|
   | `DSH_ref2av.json` | **正向替换**：输入「白模 + 绿幕」视频 + 人物参考图 + 背景参考图，输出「人物换到白模身上、背景替换绿幕」的成品视频，同时保留原视频的动作、节奏与运镜 |
   | `DSH_av2ref.json` | **反向生成**：输入任意成品视频，输出「白色无特征人偶 + 纯绿幕」的素材视频，动作与时长保持一致 |
   | `DSH_ref2av_for_milkyfrog.json` | **正向替换 · 特殊角色版**：结构与 `DSH_ref2av` 相同，但提示词改写为适配一个**略胖大肚子黄色生物**（"奶蛙"），并额外约束「不得继承源视频的人体比例」。输入奶蛙三视图 + 背景图 + 白模绿幕视频，输出**奶蛙跳舞视频** |

2. **一个自定义节点**（本仓库唯一的原创代码）：

   | 文件 | 节点名 | 作用 |
   |---|---|---|
   | `custom_nodes/comfyui_h3_frame_align.py` | `H3 Frame Rate Align` | 把参考视频的帧序列**按源帧率重采样到 24fps 语义**，并返回与 H3 帧数网格对齐的输出帧数 |

   **为什么需要它**：H3 的 `ref_videos` 输入是一个 IMAGE 批次，本身不携带帧率信息；而 H3 内部把任何帧序列都**当作 24fps**（`FPS = 24` 是硬编码常量）。所以如果源视频是 30fps / 25fps / 60fps，模型会按 24fps 去解释它，导致参考动作被加速或减速。这个节点就是把这个问题在**工作流内部**解决掉：无论你的源视频是什么帧率，输出时长都等于源时长，动作速度也保持正确。

   > 如果你只用 24fps 的素材，理论上可以不装它，但工作流里已经连线到这个节点，建议直接安装。

**不包含**：模型文件、第三方节点、任何媒体素材。

## 二、安装步骤

### 1. 安装自定义节点

把 `custom_nodes/comfyui_h3_frame_align.py` 复制到你的 ComfyUI 目录下：

```
<你的 ComfyUI>/custom_nodes/comfyui_h3_frame_align.py
```

它是一个单文件节点，**不需要额外的依赖**，复制进去后**重启 ComfyUI** 即可生效。重启后在节点搜索里搜 `H3 Frame Rate Align` 或 `fps` 就能找到（分类：`model/conditioning/minimax`）。

### 2. 安装工作流

把 `workflows/` 下的两个 JSON 复制到：

```
<你的 ComfyUI>/user/default/workflows/
```

重启后（或刷新页面）在 ComfyUI 的工作流列表里就能看到 `DSH_ref2av` 与 `DSH_av2ref`。

也可以不复制文件，直接在 ComfyUI 界面里把 JSON **拖进画布**导入。

### 3. 准备模型（本仓库不提供）

三条工作流都使用 MiniMax H3 的 **ref2va** 权重，请自行下载并放到对应目录（文件名需一致）：

| 类型 | 文件名 | 放置目录 |
|---|---|---|
| Diffusion 模型 | `minimax_h3_ref2va_pruned_int8_convrot.safetensors` | `models/diffusion_models/` |
| 视频 VAE | `minimax_h3_video_vae_int8_convrot.safetensors` | `models/vae/` |
| 音频 VAE | `minimax_h3_audio_vae_fp32.safetensors` | `models/vae/` |
| 文本编码器 | `qwen3vl_32b_minimax_h3_nvfp4_awq.safetensors` | `models/text_encoders/` |

这些是 ComfyUI 官方与 MiniMax 官方发布的模型，请从官方渠道获取（Comfy-Org 在 Hugging Face 上的 MiniMax-H3 仓库）。

### 4. 其他依赖

工作流还用到以下**本身就存在**的节点，请确认你的 ComfyUI 已具备：

- ComfyUI 核心自带的视频节点：`Load Video`、`Trim Video`（Video Slice）、`Get Video Components`、`Create Video`、`SaveVideo`
- 核心自带的 `If/Else Switch`（`ComfySwitchNode`）

## 三、使用流程

### 正向：白模 + 绿幕 → 成品（`DSH_ref2av`）

1. **节点 150 `Load Video`**：选择你的「白模 + 绿幕」源视频（放到 `input` 目录后在下拉框里选）。
2. **节点 153 `Load Image`**：人物参考图（三视图，接到 `<Picture 1>`）。
   - 想要人脸更清晰，建议**再补一张面部近景**接到 `ref_images.ref_image_2`，并在提示词里说明它是面部细节参考。
3. **节点 154 `Load Image`**：背景参考图（接到 `<Picture 2>`）。
4. **节点 138 的提示词**：已写好「白模→人物、绿幕→背景」的 Ref2VA 六段式提示词，标签与接线严格对应（`<Video 1>` = 源视频、`<Picture 1>` = 人物、`<Picture 2>` = 背景）。**如果你改了接线，必须同步改提示词里的标签**，否则模型会认错参考。
5. 直接运行。输出保存在 `output/video/`。

### 反向：成品 → 白模 + 绿幕（`DSH_av2ref`）

1. **节点 150 `Load Video`**：选择任意成品源视频。
2. **节点 138 的提示词**：已写好「成品→白模+绿幕」的提示词。
3. 直接运行，得到可用于正向工作流的素材。

### 正向 · 特殊角色版：奶蛙三视图 + 背景 + 绿幕白模视频 → 奶蛙跳舞视频（`DSH_ref2av_for_milkyfrog`）

这是 `DSH_ref2av` 的**特殊角色版**，结构与它完全相同，只有提示词不同。用于把「白模 + 绿幕」素材里的动作，套到一个**略胖大肚子黄色生物（奶蛙）**身上，并把绿幕换成背景。

**一句话**：输入 **奶蛙三视图 + 背景图 + 绿幕白模视频** → 输出**奶蛙跳舞视频**。

1. **节点 150 `Load Video`**：白模 + 绿幕源视频（建议 24fps，见 §七的输入体积注意事项）。
2. **节点 153 `Load Image`**：**奶蛙的三视图**（接到 `<Picture 1>` = `ref_image_0`）。建议把正面 / 侧面 / 背面拼成一张，或只放最有代表性的正面图。
3. **节点 154 `Load Image`**：背景图（接到 `<Picture 2>` = `ref_image_1`）。
4. **节点 138 的提示词**：已写好适配奶蛙的 Ref2VA 六段式提示词，标签与接线严格对应（`<Video 1>` = 源视频、`<Picture 1>` = 奶蛙三视图、`<Picture 2>` = 背景）。**改了接线就要同步改提示词里的标签**，否则模型会认错参考。
5. 直接运行。输出保存在 `output/video/`。

**为什么这条的提示词要单独写**：白模源视频是**人体比例**，而奶蛙**不是人**（圆形大肚子、四肢短粗、脚掌略大、裸露皮肤无衣物、无鼻子无耳朵、眼睛大且绿色）。如果沿用通用提示词，模型会把奶蛙往人体上拉，造成**比例失调**。所以这条工作流的提示词额外做了三件事：

- 明确写出 `It is not a human`，并逐项列出大肚子、短粗四肢、大脚掌、无衣物、无鼻无耳、大绿眼；
- 把源视频的人体比例也标为「占位、不得保留」（`Its human body proportions are placeholders as well and must not survive either.`）；
- 在多个分镜里反复约束「身体永不拉伸变瘦变人形、肚子保持形状、始终无衣物」（`never turns human` / `keeps its shape` / `is never dressed`）。

**效果不理想时依次试**：

1. **比例仍偏人形** → 节点 136 的 `ref_image_size` 由 `match` 改为 `max`（参考图对形状的约束更强，但更慢）。
2. **仍偏人形** → 说明**源白模素材本身的体型就偏人体**。更根本的做法是重拍 / 重生成圆胖短肢的白模素材。
3. 奶蛙若有其他显著特征（尾巴、角、花纹等）提示词未覆盖 → 在节点 138 里补写。

> 本节的三视图与背景图位置、提示词标签规则，与上面「正向」一节完全一致；两条工作流可以互相参照。

## 四、参数说明

| 参数 | 位置 | 说明 |
|---|---|---|
| `megapixels` | `ResolutionSelector` | **决定实际生成分辨率**，H3 不会夹取，你填多少就生成多少。`0.4` ≈ 832×480，`1.0` ≈ 1344×736，`1.5` ≈ 1632×928。经验值：**0.98 ~ 1.2 是画质与显存的最佳区间**；再往上属于模型的未验证区间，且 `VAEDecode` 要在所有帧上解码，显存开销会陡增 |
| `ref_image_size` | `MiniMaxH3ReferenceToVideo` | `match` = 参考图缩到生成分辨率（快）；`max` = 保参考短边 2048（人物身份与背景保真更强，但明显更慢） |
| `start_time` / `duration` | `Trim Video` | 裁剪源视频。**`duration = 0` 表示不裁剪（用整段）** |
| 时长上限 | `H3 Frame Rate Align` 节点源码 | H3 训练区间为 15 秒（362 帧）以内；节点内 `TRAINED_MAX_FRAMES = 362`。源视频超出时会被截断到该上限，需要更长请自行修改该常量 |
| `Enable Lightning LoRA` | 布尔开关（详见第五节） | `False` = 完整采样（默认 20 步，质量优先）；`True` = 4 步 turbo LoRA（快，实测可省 2.0～4.5 倍时间，分辨率越高越划算） |

## 五、LoRA 加速开关（重要）

### 开关是哪个节点

| | 说明 |
|---|---|
| **节点标题** | **`Boolean (Enable Lightning LoRA)`** |
| 节点类型 | `PrimitiveBoolean`（ComfyUI 核心自带，分类 `utilities/primitive`） |
| 它是什么 | 一个只输出 `true` / `false` 的**布尔常量**，本身不做任何计算 |
| 它控制什么 | 输出的那根线分叉接到**两个 `If/Else Switch`**，一次同时二选一 |

因为一个开关同时遥控两组二选一，所以**必须整体切换，不要拆开**：

| 开关状态 | 模型来源 | 采样步数 |
|---|---|---|
| `False`（默认） | 原始底模（`minimax_h3_ref2va_pruned_int8_convrot`） | 节点 `Int (Full)`，本仓库默认 **20** 步 |
| `True` | 底模 + 4 步蒸馏 LoRA（`minimax_h3_ref2v_turbo_4step_v0.1_comfyui_bf16`） | 节点 `Int (Lightning LoRA)`，默认 **4** 步 |

**相关的其它节点**：

- **`LoraLoaderModelOnly`**：真正加载那个 `.safetensors` 的地方，决定"用哪个 LoRA 文件"。
- **`Int (Full)` / `Int (Lightning LoRA)`**：两条路径各自的步数，都是普通整数控件，双击可改。
- 注意：`BasicScheduler` 界面上显示的步数（例如 `20`）**在 `steps` 输入被连线后即失效**，实际生效的是上面这两个 `Int` 节点的值。

### 为什么必须成对切换

- 只开 LoRA 却不降步数 → 白花时间，画质还可能因过采样变差；
- 只把步数从几十改成 4、却不开 LoRA → **画质会崩**：底模是按几十步训练的，每一步只挪一小段，4 步等于只走了应有路程的零头，潜空间远未收敛。

**结论：省时间靠"降步数"，但"降步数后还能看"必须靠 LoRA。** 想微调，只改 `Int (Lightning LoRA)`（在 `4` / `6` 之间试），不要动 `Int (Full)`，也不要拆开关的组合。

### 实测耗时（RTX 4090 48G，24 fps）

| 工作流 | 百万像素 | 输出时长 | **未开 LoRA** | **开启 LoRA** | 加速 |
|---|---|---|---|---|---|
| `DSH_av2ref` | 0.4 | 15 s | **36 min** | **18 min** | **2.0×** |
| `DSH_ref2av` | 1.0 | 15 s | **90 min** | **20 min** | **4.5×** |
| `DSH_ref2av_for_milkyfrog` | 1.0 | 9 s | — | **约 9 min** | — |

> 上表前两行是"同一工作流、同一素材"下开关 LoRA 的对照；第三行（`DSH_ref2av_for_milkyfrog`）是**开着 LoRA** 跑 1.0 MP / 9 秒素材的实测值，未测关闭 LoRA 的情形，因此加速比留空。

从这组数据可以得出三条经验规律：

1. **耗时与像素数近似线性**：未开 LoRA 时两个基准点归一化后一致（都是 `6.0 min /（秒·MP）`），说明瓶颈是显存带宽而不是算力。
2. **开启 LoRA 的实际加速是 2.0～4.5 倍，而不是步数比**：步数从 20 步降到 4 步是 5 倍，但实测拿不到满额，因为存在**与步数无关的固定开销**（模型加载与换出、参考图与参考视频编码、VAE 解码、显存带宽的最低成本）。
3. **分辨率越低，固定开销占比越大，LoRA 的加速比就越小**：0.4 MP 时只省到 `2.0×`（36 → 18 min），1.0 MP 时能省到 `4.5×`（90 → 20 min）。也就是说——**像素越高，开 LoRA 越划算**。

> 1.5 MP 及以上未在本仓库测试。注意该 LoRA 的训练标注为 768p，分辨率大幅超过 1.0～1.2 MP 属于训练分布之外，画质收益可能递减。

## 六、常见问题

**Q：为什么输出时长和我源视频一样，但动作还是被加速了？**
A：请确认工作流里的 `H3 Frame Rate Align` 节点在链路上（它的 `source_fps` 应连到 `Get Video Components` 的 `fps`）。若你手动填了帧率，请填写源视频的真实帧率。

**Q：输出被截断到 15 秒了。**
A：这是 H3 的训练上限（362 帧 @24fps）。要更长请修改节点里的 `TRAINED_MAX_FRAMES`，但超出训练区间的效果无保证。

**Q：背景中途变回绿幕了。**
A：这属于长视频的条件漂移。工作流的提示词里已在多个时间点复述背景约束；如仍有残留，可尝试把 `ref_image_size` 改为 `max`，或再补一张同背景环境的不同角度参考图。

**Q：正向工作流输出的人物不够清晰。**
A：清晰度上限主要由**参考图**决定。优先补充一张人物面部近景参考图，其次才是提高 `megapixels`。

## 七、重要：输入视频过大会导致整机卡死

**症状**：点下 Queue 后的**最初几秒**，CPU、系统内存、磁盘同时冲高，而 **GPU 显存始终不增长**，随后整机卡死或硬重启。重启后再跑**仍然复现**。

**原因**（已由 Python traceback 证实，非推测）：`Get Video Components` 节点会把**整段视频全部解码**，然后**一次性堆成单个 CPU float32 张量**：

```
comfy_extras/nodes_video.py  GetVideoComponents.execute
  -> comfy_api/latest/_input_impl/video_types.py  get_components_internal
       images = process_image_format(torch.stack(frames))   # 整段堆叠
       process_image_format = lambda a: a.float() / 255.0   # 转 float32
```

在 `ComfyUI\logs\comfyui.log*` 里可以搜到这个特征报错：

```
[enforce fail at alloc_cpu.cpp:117] data. DefaultCPUAllocator:
not enough memory: you tried to allocate <N> bytes.
```

已确认的一例，一次性申请了 **31,048,174,080 字节（约 29 GB）**。

**真正决定大小的是 `帧数 × 宽 × 高 × 每像素字节数`，不是文件有多少 MB。** 编码格式（H.264 / H.265）与码率影响很小。所以**小文件也可能解码出巨大张量**（分辨率高、帧数多），大文件只有在"高分辨率且帧数多"时才危险。实测对比：

| 输入视频 | 分辨率 | 帧率 × 帧数 | 解码后 float32 帧张量 | 结果 |
|---|---|---|---|---|
| 导致崩溃的那条 | 720 × 1280 | 30 fps × 355 帧 | ≈ 3.9 GB | **崩溃** |
| 正常工作的那条 | 864 × 480 | 24 fps × 362 帧 | ≈ 1.8 GB | 正常 |
| 同一条重新压缩后（约 1.45 MB） | — | 时长不变 | — | **正常** |

**为什么看起来像"以前一直好好的，突然就坏了"**：这个内存分配处在机器上限附近，属于**边际状态** —— 同一份日志里，**同一个视频前 4 次运行全部成功，第 5 次才爆内存**。而这次 OOM 之后，NVIDIA 驱动可能被留在复位状态（系统日志 `nvlddmkm` 事件 id 14：`GPU Reset Required` / `PF FLR`），**此后每一次运行都会以同样方式失败，直到彻底冷启动**。所以"一条坏视频"会表现得像"装机坏了"或"显卡坏了"。

**解决方法**：

1. **把输入视频重新压缩或降分辨率后再输入**（已实测：压缩后同一条工作流恢复正常）。**降分辨率是最有效的手段，减少帧数次之。**
2. 这条链路**没有流式解码**，下游救不了它 —— H3 是在**整段帧堆叠分配完成之后**才对参考视频做缩放（`adapt_canvas`），所以指望模型侧缩放来省内存是无效的。
3. 发生这类崩溃后，请**彻底关机**（不是重启）再开机，以清除驱动复位状态，否则你无法判断修改是否真的生效。
4. 页面文件过小会让卡死更严重，但**不是根因**；修好页面文件只能降低"整机卡死"的概率，不能消除 OOM 本身。

> ⚠️ **触发故障的大小 / 分辨率边界目前尚未确定**，请勿把某个具体 MB 数值当作阈值。判断新素材是否安全时，先查它的**分辨率与总帧数**，再与上表对比。
